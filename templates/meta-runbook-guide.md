# Runbook 编写规范

> 定义 `troubleshooting/runbooks/` 目录下诊断 Runbook 文档的格式规范、章节结构、决策树语法及撰写行为指南。面向 AI Agent 和人类协作者，目标是所有 Runbook 结构一致、可机械执行、可交叉引用。

---

## 1. Runbook 的定位

Runbook 是**行动导向的结构化诊断程序**，回答「看到这个现象后怎么办」。与模块文档和流程文档的分工：

| 文档类型 | 目录 | 回答的问题 | 读者 |
|---------|------|-----------|------|
| Runbook | `troubleshooting/runbooks/` | 看到现象 X，怎么诊断？根因确认后，怎么恢复？ | AI Agent（机械执行）、运维人员 |
| FAQ | `troubleshooting/faq.md` | 常见问题怎么快速定位？ | 人类运维（快速参考） |
| 模块文档 | `modules/` | 这个模块怎么工作？有什么已知陷阱？ | AI Agent（理解深层原因） |
| 流程文档 | `flows/` | 正常路径下数据怎么流转？ | AI Agent（对比异常） |

**核心设计理念**：
- Runbook 是一个**可机械执行的检查清单**，Agent 不需要理解系统全貌也能执行诊断
- 每一步都有**明确的分支条件**（"如果输出是 X，跳转到 §Y"），不留模糊判断空间
- 恢复步骤**可直接复制执行**，包含完整的命令、参数和验证方法

    └── ...
```

## 3. Frontmatter 规范

每份 Runbook 以 YAML frontmatter 开头：

```yaml
---
id: <kebab-case-id>           # 唯一标识，与文件名一致（不含 .md）
title: "<标题>"                # 简洁描述该 Runbook 处理的症状
severity: critical | major | minor   # 症状严重度
affected_modules: [<列表>]     # 涉及的模块 id（必须存在于 modules/ 下）
---

# <标题>

> 一句话描述该 Runbook 处理的用户可观察症状。
```

**约束**：
- `id` 与文件名一致，`symptom-index.yaml` 通过 `id` 引用 Runbook
- `severity` 三个级别：`critical`（数据不可访问/服务不可用）、`major`（部分功能异常）、`minor`（体验问题）
- `affected_modules` 用于影响链分析和 maintain-kb 增量检查定位
- frontmatter 后紧跟一级标题和 blockquote 摘要

## 4. 必选章节

每个 Runbook 必须包含以下四章。

### §1 症状确认

**目的**：缩小故障范围，确认问题性质和影响面，排除明显无关的分支。

**结构规范**：
- 按从外到内的顺序排列检查步骤（先外 → 全局状态 → 局部细节）
- 每一步使用三级标题（`###`）
- 每一步包含三个要素：**检查命令**（代码块）、**预期输出表格**（Markdown 表格）、**下一步跳转**（`→` 箭头指向同文档内的 §2.x 或跨 Runbook 引用）

**表格约定**：

```markdown
| 观察到的输出/现象 | 判断 / 下一步 |
|------------------|--------------|
| 输出为 X | → 根因候选 A，跳转 §2.1 |
| 输出为 Y | → 根因候选 B，跳转 §2.2 |
| 输出为 Z | → 继续 §1.x（深入检查） |
```

表格至少包含两行（至少一个分支条件 + 一个"继续"或"其他"兜底行）。当某行指向跨 Runbook 引用时，使用完整路径：`→ Runbook: [other-runbook](other-runbook.md)`

### §2 诊断决策树

**目的**：从 §1 缩小后的范围出发，逐层深入定位根因。

**结构规范**：
- 每个子节对应 §1 的一个分支，使用三级标题：`### 2.x <分支名称>`
- 检查步骤按**概率从高到低**排列（最可能的根因最先检查）
- 每一步同样包含三个要素（检查命令 + 表格 + 跳转）
- 当某分支的根因已在上游 Runbook 中覆盖时，直接引用
- 当到达终端诊断（无法进一步缩小）时，明确标注：`→ 至此已到诊断终点，建议收集日志联系研发`

**表格中的引用约定**：
- 同文档跳转：`→ 跳转 §3.A`
- 跨 Runbook 引用：`→ Runbook: [<other-id>](<other-id>.md)`
- 跨 KB 文档引用：`→ [<title>](../modules/<id>.md#<anchor>)`

### §3 恢复步骤

**目的**：针对每个确认的根因，提供可执行的恢复操作序列。

**结构规范**：
- 每个根因使用三级标题：`### §3.<大写字母> —— <根因名称>`
- 步骤使用有序列表（`1.` `2.` `3.`），每步包含：
  - **操作描述**：做什么（非技术视角）
  - **命令**：代码块，完整命令（含参数），可直接复制
  - **验证**：操作后如何确认成功
- 恢复步骤末尾必须包含「恢复后验证」子步骤，确认问题已消失
- 若恢复涉及数据破坏风险，在步骤前使用 `> ⚠️ **警告**：...` 标注

### §4 关联参考

**目的**：链接到更深层的技术文档，供 Agent 在关键决策点查阅。

**格式**：Markdown 表格。

```markdown
| 文档 | 关联点 |
|------|--------|
| [模块文档](../../modules/<id>.md) | 本 Runbook §2.x 涉及的深层机制 |
| [流程文档](../../flows/<id>.md) | 正常路径对比 |
| [FAQ 条目](../faq.md) | 可快速参考的已知问题 |
```

## 5. 可选章节

### 5.1 复合故障处理

当该症状可能由多个并发根因导致时，在 §3 末尾增加此章节，描述：

- 复合故障的典型表现（恢复了一个问题但症状未完全消失）
- 多轮排查的建议顺序

### 5.2 已知 Bug 关联

当该 Runbook 的某些根因对应 `known-bugs.md` 中已记录的缺陷时，增加此章节：

```markdown
| Bug ID | 关联点 | 临时缓解措施 |
|--------|--------|------------|
| BUG-001 | §2.x 中的某根因 | 描述临时恢复动作 |
```

## 6. 决策树编写规范

### 6.1 检查步骤的"三要素"

```
#### 检查标题（做什么）

命令描述性文字。

```shell
具体命令
```

| 输出/现象 | 判断 / 下一步 |
|-----------|--------------|
| 输出匹配 A | → 含义解释，跳转 §X.Y |
| 输出匹配 B | → 含义解释，跳转 §X.Z |
| 其他 | → 兜底处理 |
```

### 6.2 分支条件设计

- **必须闭合**：表格的最后一行必须是兜底条件（"其他" / "不匹配任何已知模式"），确保 Agent 不会因未预期的输出而卡住
- **优先匹配具体值**：表格行按精确匹配 → 模式匹配 → 兜底 的顺序排列
- **明确"正常"**：如果某输出表示"系统正常，问题不在这一层"，必须显式列出并指向"继续下一检查"

### 6.3 诊断顺序原则

1. **检查成本从低到高**：先跑轻量命令，再跑耗时/破坏性操作
2. **根因概率从高到低**：高频故障模式优先检查
3. **影响面从大到小**：先判断是全局性问题还是局部性问题
4. **从外到内**：先检查外层（服务/进程是否运行），再深入到底层组件

### 6.4 引用风格

| 引用类型 | 写法 |
|---------|------|
| 同文档内跳转 | `→ 跳转 §2.3` 或 `→ 根因 B：xxx，跳转 §3.B` |
| 跨 Runbook | `→ Runbook: [<id>](<id>.md)` |
| 跨 KB 模块文档 | `→ [<title>](../../modules/<id>.md#<anchor>)` |
| 跨 KB 流程文档 | `→ [<title>](../../flows/<id>.md)` |
| FAQ 条目 | `→ [FAQ QN](../faq.md#qN)` |

## 7. 与 symptom-index.yaml 的关系

- `symptom-index.yaml` 是 Runbook 的**检索入口**，AI Agent 通过它定位到具体的 Runbook 文件
- 每新增一个 Runbook，必须在 `symptom-index.yaml` 中至少注册一条路由
- 同一个 Runbook 可被多条路由指向（不同用户表述映射到同一个诊断程序）
- `symptom-index.yaml` 中 `runbook_id` 字段必须与 Runbook frontmatter 的 `id` 一致

## 8. 撰写行为指南

### 8.1 假设读者是 AI Agent

- 命令使用完整的路径或环境无关的路径变量（如 `<installdir>`、`$PROJECT_ROOT`）
- 避免"通常""可能"等模糊词——写"预期输出为 `Started`"，不写"应该显示 Running 状态"
- 分支表格的每一行都是 Agent 的判断依据，不要出现"参考上文"的隐含依赖

### 8.2 基于现有知识库编写

- 每个诊断步骤的"为什么"应从已有模块文档中验证
- 根因分析应引用模块文档 §6「已知陷阱」和 flow 文档中的异常路径
- 命令参数和输出格式应与实际代码行为一致（必要时读取源码确认）

### 8.3 优先覆盖稳定行为

- 仅覆盖已上线的稳定产品行为
- 标记为"实验性"或快速迭代的功能暂不编写 Runbook
- 涉及 CLI 命令时，确认该命令在当前版本中存在且参数格式稳定

### 8.4 代码路径引用

- 当诊断步骤依赖特定的代码行为（如错误码含义、状态机转换条件）时，在说明文字中引用代码位置，**用符号名锚定**（如 `` `<File>.cpp` 中 `<FunctionName>()` ``）
- **禁止使用行号引用**——行号会随代码修改漂移，需要用函数名/常量名等符号名定位

## 9. 检查清单

新建 Runbook 时，按以下清单逐项检查：

- [ ] Frontmatter 包含 id / title / severity / affected_modules
- [ ] id 与文件名一致
- [ ] 一级标题与 title 一致
- [ ] 标题下方有 blockquote 一句话摘要
- [ ] §1 症状确认：至少包含 1 个检查步骤，每个步骤含命令 + 表格 + 跳转
- [ ] §2 诊断决策树：每个分支有独立的 `###` 子节，按概率排序
- [ ] §3 恢复步骤：每个根因有独立子节（§3.A / §3.B ...），步骤包含命令 + 验证
- [ ] §4 关联参考：至少包含 1 条到模块/流程文档的链接
- [ ] 所有分支表格的最后一行是兜底条件
- [ ] 跳转标签（如 §3.A）在 §3 中确实存在
- [ ] `symptom-index.yaml` 已新增对应路由条目
- [ ] `index.yaml` 的 `troubleshooting` 段已新增 runbook 条目
- [ ] 全文无行号引用（用符号名锚定代码）
